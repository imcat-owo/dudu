# 嘟嘟自托管节点（Dudu Host）设计方案（2026-10-06）

> 状态：**设计稿，等她拍板**。代码一律没动。Phase 2 云模式按这份设计开工。
> 对标：Aru Host（aevella/aru-host，Apache-2.0，源码级已验证）＋ aru-collaborator-format v1。
> 她的决定是这份设计的宪法，逐条列在"§0"。

## §0 她的决定（不可谈判）

1. **云 = 她自己的服务器**，不是厂商服务器。她有云服务器（A），key 和数据全在自己手里——这是她"不预配 key"路线的终极形态。
2. **Host 是唯一数据真相**；手机只存配对凭证和可见投影。**但 Host 看得见聊天内容**（见 §3 实话条）：请求经 Host 转发、主动回合要读对话才能跑——这是结构性必然，不是 bug。她选云模式，就是选了"服务器看得见"，文档里写明白，不藏。
3. **双模式架构已定**：默认纯客户端（key 在 App 里配、聊天从手机直连模型、数据存手机本地）；云模式可选，两套她自己控制随时切换。
4. **离线不死**：她断网/服务器挂了，手机继续本地模式全功能跑。
5. **主动三件套已定**（保活方案 2026-10-05）：有活→保活顶着不被冻住；没活→老实冻住；定时唤醒→定期起来看一眼。云模式 = 真·长期驻留。
6. **授权口径**：她已授权的，主 AI 和子代理随便用，不反复弹窗。出 App 的（相册、定位、对外发送等）必须经她授权。
7. **铁律**：缺口只能补，不许靠删功能对齐。

## §1 形态：一台她自己的小电脑

```
┌──────────────┐   配对(扫码)    ┌─────────────────────┐
│   iPhone      │ ◄──────────► │  Dudu Host           │
│  嘟嘟 App     │  TLS+配对密钥 │  她的云服务器 A       │
│              │              │  (Docker, 2核2G够用)  │
│ - 配对凭证    │   数据同步    │                      │
│ - 可见投影    │ ◄──────────► │ - 唯一数据真相        │
│ - key 留底    │   (她在线时)  │ - 她的 API keys(复制) │
│   全功能      │              │ - 定时任务/主动约定   │
│              │   APNs 推送   │ - 有界执行副本        │
└──────────────┘ ◄────────── │ - 备份仓库            │
       ▲                     └─────────────────────┘
       │ 手机休眠时：Host 跑主动回合，做完经 APNs 推回手机
       │ (抄 Aru 的闭环：有界只读执行副本 → 推送 → 回到原对话)
```

跟 Aru 的对照：

| Aru 的做法 | 嘟嘟的版本 | 差异 |
|---|---|---|
| Host 装在用户 Mac/Win/Linux/VPS，iPhone 扫码配对 | 一样：她的云服务器 A 跑 Docker，App 内扫码配对 | 嘟嘟先只做云服务器形态，不做 Mac/Win 客户端（她就一台服务器） |
| 手机本地协作者和电脑协作者**不串库** | 人设隔离口径一致：云端人设和手机本地人设不串库，同一人设云↔端数据互通 | 嘟嘟是"同一人设两处互通"，Aru 是"两处各养一个"——嘟嘟更贴她的用法 |
| 协作者交换格式 v1（.arucollab）带着历史搬家 | dudu-exchange v1 已落地（2026-10-06）：Cherry/ChatBox/SillyTavern 适配器 | 嘟嘟先做了迁入，Host 侧复用同一套格式 |
| 主动约定：one_time/daily/interval，Host 跑，APNs 推回 | 主动约定系统已落地（initiative/ 模块，2026-10-05）：规则引擎在手机上；Host 版是同一套规则换个执行地 | 规则格式不变，执行器多一个"云端执行"后端 |
| 端到端加密的外部触发（Host 只存密文） | Phase 2 排后：等真有外部触发需求再做 | 先不做，诚实写在这里 |

## §2 配对流程（手机 ↔ 她的服务器）

1. 她在服务器上 `docker run dudu-host`，容器打印一次性配对码（6 位数字 + 二维码，15 分钟过期）。
2. App 里「设置 → 云模式 → 配对我的服务器」扫码或输码。
3. TLS 握手（自签名证书 pinning，首次配对时确认指纹——SSH 那套"首次确认"的老办法）。
4. 配对成功：手机存**配对凭证**（device id + 配对密钥，进 SecureStore），服务器存设备公钥。**配对密钥只换不传**：后续所有请求用配对密钥做 HMAC 签名，不在网络上传密钥本身。
5. 解绑：App 内一键解绑 → 手机删凭证，服务器删设备（她也可以在服务器上手动删）。

安全线：
- 服务器只认配对过的设备；陌生设备连上来直接拒绝，不给任何信息（防扫描）。
- 所有传输 TLS 1.3；静止数据（她的 keys、聊天记录）在服务器上 AES-256-GCM 加密，密钥由她的登录口令派生（她设一个 Host 口令，存在她脑子里，不在任何地方明文存）。
- 日志里永不出现 key（跟 App 内规矩一致：request/header 只记 model/endpoint/toolCount）。

## §3 谁跑什么（Host vs 手机）

| 能力 | 手机（本地模式） | Host（云模式开时） |
|---|---|---|
| 聊天（直连模型） | 跑（现状） | **实话**：聊天界面永远在手机上，但云模式下请求经 Host 转发——Host 结构上看得见请求和回复明文（不转发就做不了）；主动回合要读对话才能跑，Host 也看得见。她选云模式就是选了"服务器看得见"，这是她自己的服务器，不是厂商。 |
| API keys | SecureStore（现状） | **留一份在手机**：key 是"复制"到 Host，不是"搬走"。每把 key 她自己选要不要在手机留底（默认留）。云模式下请求经 Host 转发（key 在 Host 内存里）；断网切本地时用手机里的底继续全功能跑，不哑。 |
| 主动约定（initiative/） | 前台 tick + 通知预排（现状） | **接管执行**：到点 Host 跑主动回合（同一套规则格式），做完经 APNs 推回手机 |
| 任务进度小卡片 | App 内 UI（现状） | Host 回合的进度经推送同步到卡片 |
| 备份 | 本地文件（现状） | Host 当备份仓库：自动收她的备份文件（WebDAV/S3 目的地已支持，加一个"dudu-host"目的地） |
| 稍后告诉她 / outreach | 本地（现状） | 复用 initiative 通道，Host 侧同一套 cap |
| 保活 | 三件套（已定） | **云模式 = 真·长期驻留**：手机可以彻底冻住，Host 那边一直醒着 |

**Host 不碰的东西**：她的相册、定位、蓝牙等手机原生能力——那些永远只在手机上，按她的授权口径走。Host 是"云端大脑+定时器"，不是"云端手机"。

## §4 离线时发生什么（她断网 / 服务器挂了）

- 手机检测到 Host 不可达（3 次心跳失败）：**自动、无感切回本地模式**，顶部给一个小提示（"云端连不上，已切回本机"——可爱不油腻的腔调）。
- 本地模式 = 现在这套，全功能：聊天直连、主动约定走前台 tick、备份存本地。**不断网哑**：手机里留了 key 的底（她自己选的，默认留），断网切本地时直接用底继续跑，不许出现"连上服务器或重新填 key 才能用"。她主动删掉手机里的底，那是她的选择，后果她自己担，App 里写明白。
- 恢复连接后：手机把离线期间的新数据（聊天记录、主动规则变更、日记等）推给 Host 合并。合并规则：**按时间戳 last-write-wins，删除永不自动传播**（她删掉的东西，Host 不许复活它——这是底线）。
- 冲突（两边同时改了同一条）：保留两份，把冲突的那条标出来让她定，不许 AI 自作主张丢一份。

## §5 跟已落地的两套系统的衔接

**主动约定（initiative/，2026-10-05 落地）**：
- 规则格式不变（one_time/daily/interval，slot 台账，一人设一规则，每日上限 3，中断不重试）。
- Host 侧新增一个执行后端：同样的 `checkDueInitiatives`，跑在服务器上。手机开云模式后，本地的前台 tick 自动让位（Host 是真相，手机是投影——到点谁跑，真相说了算）。
- 防打扰铁律在云端同样生效：cap、grace 窗口、不重试，一个不少。

**Harness（Phase 1 已审过，Phase 2 待做）**：
- Phase 1 的 session log / tool registry / hooks 全在手机上，Host 不需要重做。
- Harness Phase 2（保活移植）做的时候，云模式就是答案的一半：手机冻住时，"有界只读执行副本"交 Host 跑——这正是 Aru 跑通的那条链，嘟嘟的 harness 日志格式让"执行副本"有现成的回放载体（session log 本来就是为 resume/replay 设计的）。
- 顺序：Host 先立起来（配对+数据同步+主动接管），Harness Phase 2 再把执行副本交过去。

## §6 不做的（诚实清单）

- 不做多设备多手机：先只认一台 iPhone（她的）。多设备是 Phase 3 的事。
- 不做端到端加密的外部触发：等真有"第三方事件唤醒 AI"的需求再做，现在用不上。
- 不做 Host 上的聊天界面：聊天界面永远在手机上。但实话写在 §0#2 和 §3：云模式下请求经 Host 转发、主动回合读对话，Host 结构上看得见明文——这是她自己的服务器，她选之前就知道。
- 不追求 Host 的"无限常驻执行"：Host 只在有主动规则/定时任务时才跑回合，没活就闲着（跟她"无任务不保活"的口径一致，省服务器资源）。

## §7 验收标准（到时按这个审）

- **第 0 步先行**：推送先测。她的 IPA 是自己签的，自签通常拿不到 APNs 推送权限——没把握，所以开工第一步就是真机验证推送能不能到。推不回手机，整条主动链（Host 跑回合→推送→回到对话）就断了，后面全白做。推送不通时的 fallback（本地定时通知 / 打开 App 时轮询拉取）是拍板点，测完再定。
- 三条死线：数据在手机↔Host 间不断层、联动真连上（配对→同步→主动→推送整条链）、没有死按钮。
- 配对全程她只扫一次码，之后无感。
- 断网/服务器挂了，手机自动切本地，数据不丢，恢复后合并无冲突丢失。
- 密钥永不进日志、永不明文落盘（审计时 grep）。
- 真机验收：通知真的响、点通知真的回到对话、Host 挂了手机真的能自己跑。

## §8 开工顺序（Phase 2 拆步）

0. **先测推送**：她自签 IPA 的真机上验证 APNs 推送能不能到。通了再往下走；不通则先定 fallback（本地定时通知 / 打开 App 轮询拉取），再决定主动链怎么做。
1. Host 最小可用：Docker 镜像 + 配对 + 健康检查（她先能把容器跑起来）。
2. 数据同步：手机↔Host 双向同步（last-write-wins + 删除不传播 + 冲突标出）。
3. Keys 复制：key 复制到 Host，手机留底（她自己选，默认留）；云模式请求经 Host 转发。
4. 主动接管：initiative 执行后端换到 Host，APNs 推回。
5. 备份仓库：Host 收备份文件。
6. Harness Phase 2 再把"有界执行副本"交过去（另起方案，不在本篇）。

## §9 小补充（可以等的两行）

- 配对码输错 5 次锁定 15 分钟，防暴力猜。
- 服务器重启后，Host 静止数据是 AES-256-GCM 加密的，解密要她输 Host 口令——重启后她不输口令，Host 就是个空壳（主动任务不跑、转发不工作），等她输了才醒。这是诚实的代价，写在这里。
